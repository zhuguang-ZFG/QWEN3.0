# 全量仓库审查

## Goal

对当前 `main` 分支的 DLC 绘图服务及其 `esp32S_XYZ` 子模块进行证据驱动的全量审查，识别会影响正确性、安全、可靠性、设备运动安全、可维护性、测试有效性和发布可靠性的真实问题；审查结论复核无误后，实施全量修复与改善并通过所有适用门禁。

## Background

- 审查基线为 2026-07-16 的 `main`，初始工作树干净，根仓库提交为 `c8383a84`。
- 生产主链路为 `server_dlc.py → dlc_api/ → dlc_core/ → device_gateway/ → ESP32`；另含 `dlc_mcp/`、设备 App API、语音 ASR、小程序和部署脚本。
- `esp32S_XYZ` 是独立 Git 子模块，包含固件运动栈与 `manager-mobile` 小程序。
- 旧 `routing_engine*`、旧聊天栈等已退役内容不作为当前生产缺陷主体；归档仅用于核验文档或残留引用。

## Requirements

- R1：盘点仓库结构、运行入口、依赖、配置、测试与生成/归档边界，建立审查覆盖矩阵。
- R2：审查 Python 服务的 API、鉴权、输入验证、异步/并发、状态持久化、错误处理、资源生命周期和跨层数据流。
- R3：审查设备网关、任务队列、WebSocket、设备身份、家庭审批、G-code/Grbl 下发边界与运动安全契约。
- R4：审查语音链路、MCP、小程序及固件中与云端协议一致性、鉴权和失败语义相关的实现。
- R5：审查部署、配置、密钥处理、健康检查、回滚、依赖锁定和生产默认值。
- R6：运行适用的静态与动态门禁，包括 `pytest`、`ruff check .`、`pyright`、代码大小检查，以及运动/G-code 范围的 fz `agent_gate --profile standard`；子模块按其现有工具链运行可离线执行的门禁。
- R7：检查测试是否覆盖真实行为，特别排除恒真测试、错误 mock 边界和只验证实现细节的测试。
- R8：所有高/中严重度发现必须人工回溯真实调用链并给出文件与行号、触发条件、影响和最小修复建议；无法复现或证据不足的项目明确标为风险/待确认，不冒充缺陷。
- R9：严格分阶段执行：先冻结审查基线并完成缺陷复核，再修改产品代码；不得用修复后的行为反推审查结论。
- R10：修复阶段覆盖所有已确认的 Critical/High/Medium 缺陷；Low、设计债务和测试缺口在不引入不成比例复杂度的前提下按 Ponytail 最小变更原则改善，未修项目必须给出明确理由和残余风险。
- R11：每项修复必须有针对性回归证据；跨层契约变更同步更新生产者、消费者、schema/类型、测试与必要文档。
- R12：保留用户已有改动；未经用户明确要求不部署、不提交、不推送。固件、小程序与运动栈修改前加载对应领域 skill，运动/G-code 变更后强制通过 fz `agent_gate`。

## Acceptance Criteria

- [ ] AC1：覆盖矩阵列出所有当前生产模块、子模块、测试、配置和部署边界，并标明审查方式与结果。
- [ ] AC2：所有适用门禁均有命令、退出状态和失败摘要；因环境或网络无法运行的门禁有明确限制说明。
- [ ] AC3：最终报告按 Critical/High/Medium/Low 排序；每条缺陷含文件:行号、证据、影响、复现/触发条件和修复方向。
- [ ] AC4：至少核验一条完整云端→网关→设备运动数据流，以及小程序/语音/MCP 各自的关键鉴权与失败路径。
- [ ] AC5：审查文档区分已确认缺陷、设计债务、测试缺口和环境限制，不把已退役代码或可信内部数据误判为线上漏洞。
- [ ] AC6：结论明确说明残余风险、未覆盖面及建议修复顺序；若无某严重度发现，也明确写明。
- [ ] AC7：所有已确认 Critical/High/Medium 缺陷完成修复并具备能在修复前失败、修复后通过的直接或等价回归证据。
- [ ] AC8：适用的根仓库、子模块、小程序、固件和 Host SIL 门禁最终通过；任何无法执行或未通过项目均不得宣称完成。
- [ ] AC9：最终逐项核对审查发现、修复提交范围、测试证据和残余风险，确认没有遗漏的已确认问题。

## Out of Scope

- 不部署生产、不烧录真机、不提交或推送 Git，除非用户之后另行明确要求。
- 不对 `docs/archive/` 中已退役实现做等同于生产代码的逐文件审查。
- PC Host SIL 不能替代纸路、蓝牙和真机验证；报告必须保留该限制。
